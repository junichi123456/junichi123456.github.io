# R11 のエアームドの持ち物 比較評価 仕様書

作成: Opus 5.5 ／ 実装: Sonnet 5.5（`model: sonnet`）／ 受け入れ確認: Opus 5.5
対象構築: `pokechamp/tool/data/party/R11.json`（＝`ADOPTED.json`＝`S4_8.json`、3つとも同じ内容であることを確認済み）
作業フォルダ: `pokechamp/tool/`（Linux は `python3`、Windows は `python`）

「事実」はコードとデータで確認した内容。「仮説」は本評価で確かめる内容。

対象外: Star Crusade（ルートの `index.html`・`starcrusade/`）、`game_watch.py`、OCR 関連、`team.py`、`battle.py`・`engine.py`・`refine.py`・`search.py`（変更しない）、`data/*.json`（`data/party/I5_*.json` の新規作成だけは行う）、既存の結果ファイルと既存のサブコマンド。

## 0. 目的

R11 の4番目（エアームド＠ゴツゴツメット）の**持ち物だけ**を §2 の4候補に差し替え、SPEC_SLOT4 と同じ条件（規則なし・ブラインド・自5手/相手3手）で、**基準＝`logs/refine/slot4_8.json` の100戦と同じ相手・同じ種**で戦わせる。平均勝率が上がる持ち物があれば採用する（採用基準は §5、数字で決める）。

変えないもの: 他の5体のすべて、エアームドの種族・特性（がんじょう）・性格（わんぱく）・努力値（H32 B32 D2）・技（はねやすめ／ふきとばし／ボディプレス／てっぺき）・`label`。持ち物を変えても技・努力値は**変えない**（固定）。ユーザーの指定どおり範囲は「エアームドのみ」。

## 1. 前提（コードとデータで確認した事実）

### 1.1 パーティの読み込み
- `core_test._init_party(tag)` は `refine.load_tag(tag)` → `_BASE_SPECIES` をそのパーティの種族に合わせる → `refine.apply_party` → `battle.MY_TYPES` 再計算 → `refine.teams()`。`load_tag('I5_1')` は `R<数字>` 以外なので `data/party/I5_1.json` を読む。`load_tag('R11')` は `data/party/R11.json`。

## 2. 候補（ここで確定。実装側で変えない）

基準（候補0）= ゴツゴツメット。比較する持ち物は次の4つ。いずれも他の5体（オボンのみ・セグレイブナイト・たべのこし・こだわりスカーフ・きあいのタスキ）と重複しない。

| 番号 | 持ち物 | engine ID | 使用率（usage_sets、エアームド） | 狙い |
|---|---|---|---|---|
| 1 | レッドカード | `redcard` | 10.0%（ゴツメ・メガストーンに次ぐ3位） | 殴ってきた相手を1回強制交代させる。積んだミミッキュ（のろい／つるぎのまい）・メガグソクムシャ・相手エアームドのボディプレス（17回）・スカーフイダイトウを「ふきとばし（優先度-6）を待たずに」流し、ステルスロック（カバルドン）の削りを重ねる。 |
| 2 | オッカのみ | `occaberry` | 0.3% | 炎半減。メガガブリアスZのかえんほうしゃ・だいもんじ、メガリザードンXのフレアドライブ（リザードンX+ミミッキュ軸）、メガボーマンダの炎を一度だけ半分にして、はねやすめ／てっぺきの起点を作る（§1.5）。 |
| 3 | ソクノのみ | `wacanberry` | 0%（データに無い。engine には実装あり） | 電気半減。基準でエアームドを倒した技の最多クラス（10まんボルト 3＋でんこうそうげき 2＝5回）。ブリジュラス（鋼・受け軸、C11）に居座ってボディプレスを通すため。 |
| 4 | メンタルハーブ | `mentalherb` | 1.1% | ちょうはつ・アンコールを1回解除。てっぺき／はねやすめ主体なので、相手エアームドのちょうはつ（基準でエアームドを選出した6構築中2つ）やアシレーヌ・イエッサンのアンコール（てっぺき固定）で止まるのを防ぐ。 |

### 2.1 外したもの（理由）
- たべのこし（7.4%）・オボンのみ（6.3%）・きあいのタスキ（0.2%）: パーティ内で重複（ドヒドイデ・カバルドン・グレンアルマ）。
- エアームドナイト（12.8%）: メガストーンが2つになり（1試合1回のメガは `mega_used` で片方しか使えない）、`battle.py` の自分側のメガ処理は種族名でメガ形を持たせる方式（R11 は `メガセグレイブ` を直接書いている）なので、持ち物の差し替えだけでは評価できない。範囲外。
- ラムのみ（0.6%）: エアームドは鋼で毒にならず、やけど源が 0、ねむりはあくび（5構築）だけで、エアームドはふきとばし・交代で対応できる。4枠のうちメンタルハーブ（ちょうはつ・アンコールは12構築ぶんと多い）を優先。
- ひかりのこな（0.4%）: 命中率を下げるだけの運要素で狙いが立たない。
- あつぞこブーツ・おんみつマント・とつげきチョッキ等: このデータに無い（`item_id` が `''`）。

### 2.2 持ち物を変えたときの技の運用（技は変えない。確認事項としてレポートに載せる）
- **ボディプレス**: 防御の実数値と防御ランクで威力が決まり、どの候補でも火力は変わらない。ゴツメを外すと接触技（おはかまいり・相手のボディプレス・ドラゴンテール・フレアドライブ・じゃれつく等）への 1/6 の削りが無くなる。
- **ふきとばし**: レッドカード（1）は「受けたら流す」と役割が重なる。カードを使った後はふきとばしだけが流し手段になる。他の候補では役割は変わらない。
- **てっぺき／はねやすめ**: メンタルハーブ（4）はちょうはつ・アンコールに対して1回だけ守る。半減実（2・3）は抜群技を受ける回数を1回増やし、はねやすめの回数を稼ぐ。
- **がんじょう**: 全候補で同じ（満タンからの一撃は耐える）。半減実は「がんじょうが残っていないとき」の保険。
- どの候補でも**技・努力値・性格は変えない**（変える必要があっても本評価では変えない）。

## 3. 評価設計（確定）

### 3.1 条件（基準 slot4_8 と同じ）
- 規則なし（`blind_play` の `rules=None`）、ブラインド（`know=False`）、自分5手・相手3手（`OPP_DEPTH`）、最大30ターン、`trace=True`。
- 相手: `core_test.EVAL_IDS` の20構築。**相手の選出は `cores_R9.json` の `plan[kid]['opp_order']`**（slot4_8 の `plan[kid]['opp_order']` と同じものであることを §4.2 で assert）。
- 自分の選出: 候補ごとに `_init_party(f'I5_{n}')` のあと `refine.blind_select(t)`（`order_filter=None`）で再計算。`[best, top3]` を保存。
- 種: `core_test.seed_of(kid, k)` = crc32(f'core{kid}{k}')、k=0〜4。**1候補 100戦（20構築×5）を一度に回す**（段階分けなし）。
- 基準の数字は slot4_8.json から読む（再計算しない）。対は同じ (kid, k)。
- 見込み時間: 平均45秒×100戦÷4並列 ≈ **約19分/候補**、4候補で約1時間20分。選出の再計算は 1構築 約3秒（1候補 約1分）。

### 3.2 基準の再現確認（候補0、`logs/refine/item_R11.json`）
- 選出: タグ `R11` で20構築の `blind_select` を再計算し、slot4_8 の `plan[kid]['my_order']` と一致する数（目標 20/20）。
- 再現: `EVAL_IDS` の先頭5構築の k=0 を、slot4_8 の選出・相手の選出・種で本仕様のワーカー経由で再実行し、`res` と `log` が slot4_8 と一致する数（目標 5/5。4/5 は注記付きで可、4 未満なら本番を始めずに Opus に報告）。
- `item_R11.json` は確認用。基準の数字には使わない（基準は slot4_8 のまま）。

## 4. 実装

すべて `core_test.py` に**追記**する（既存の関数・定数・サブコマンドの挙動は変えない。`slot4-*` もそのまま）。既存関数（`_init_party`・`_diff_parties`・`seed_of`・`_team`・`_cores_raw`・`cores_of`・`_todo`・`_norm`・`_work_slot4`（呼ぶだけ、変更しない）・`refine.blind_select`・`refine.blind_play`・`refine.sig`・`safeio.write_json`）は使ってよい。`slot4-run` を書き換えて `--party` を足す案は採らない（`s4_head` が `base_sig`=R9 で照合するため既存の結果ファイルの意味が変わる）。

### 4.1 定数と `item-build [--force]`
- `ITEM_CANDS = {1: ('レッドカード', 'redcard', '<狙い1行>'), 2: ('オッカのみ', 'occaberry', ...), 3: ('ソクノのみ', 'wacanberry', ...), 4: ('メンタルハーブ', 'mentalherb', ...)}`（§2 の表）。`ITEM_BASE = ('ゴツゴツメット', 'rockyhelmet')`。
- `R11.json` を読み、4番目（添字3、種族がエアームド・持ち物がゴツゴツメットであることを assert）の `item` だけを差し替えた `data/party/I5_<n>.json`（n=1〜4、`json.dump(..., ensure_ascii=False, indent=1)`）を作る。既にあって同じなら書き直さない。違えば `--force` 無しでは止める。
- 検証（1つでも NG なら終了コード1）:
  1. `_diff_parties(I5_n, R11)` の差分がちょうど1件で `[3].item`。
  2. `_init_party(f'I5_{n}')` が assert なしで通る（持ち物の重複なし）。
  3. `battle.engine_game(['エアームド', 'カバルドン', 'ドヒドイデ'], ['ガブリアス', 'フラエッテ', 'カバルドン'])` の自分の先発の `item` が §2 の engine ID と一致、`ability == 'sturdy'`、`set(moves) == {'roost','whirlwind','bodypress','irondefense'}`。
  4. 他の5体の engine 上の持ち物が R11 と同じ（`sitrusberry` 等。`engine_game` に6体のうち該当3体ずつを2回渡して確認してよい）。
  5. 最後に `_init_party('R11')` に戻し、エアームドの engine 上の持ち物が `rockyhelmet` に戻る。
- 各候補 1 行出力: 番号・持ち物・engine ID・検証結果。

### 4.2 `item-run --cand N [--procs P] [--max-games M] [--force]`
- `--cand 0` は §3.2 の再現確認（タグ `R11`）。`--cand 1〜4` は候補（タグ `I5_<n>`）、k=0〜4 の100戦。
- 結果ファイル `logs/refine/item_<N>.json`（N=0 は `item_R11.json`）:
  ```json
  {"version": 1, "cand": N, "tag": "I5_N", "item": "レッドカード", "sig": refine.sig(パーティ),
   "base_sig": refine.sig(R11), "baseline_sig": slot4_8.json の sig, "source_sig": cores_R9.json の sig,
   "policy_version": policy.POLICY_VERSION, "depth": [5, 3],
   "plan": {kid: {"my_order": [...], "my_top": [...], "opp_order": [...], "sec": 秒, "same_as_base": bool}},
   "games": {"<kid>|<k>": blind_play の戻り値 + seed, sec, tag}}
  ```
  開くときに `version`・`sig`・`base_sig`・`baseline_sig`・`source_sig`・`policy_version`・`depth` を照合し、違えば止める（`--force` で日時付きに退避して新規）。起動時に slot4_8.json の `sig == refine.sig(R11)`、全 kid で slot4_8 と cores_R9 の `opp_order` が一致することを assert。
- 選出は未計算の構築だけ計算し**1構築ごとに保存**。`same_as_base` = slot4_8 の `my_order` と同じか。
- 試合は `multiprocessing` Pool（fork、無ければ spawn）・`imap_unordered`・**1戦ごとに `safeio.write_json` で保存**。ワーカーは既存の `_work_slot4` をそのまま使う（job の形 `(key, tag, party, kid, my_order, opp_order, seed)` が同じ。先頭で `_init_party(tag)` するので spawn でも可）。
- `res` が None（例外）の試合は未完了扱いで次回再試行。済んだ試合は飛ばす。`--max-games` で今回の実行数を制限。
- 進捗表示: `[済/全体] kid8|k 勝/負 nT 秒 経過分 基準○/×`。最後に「この実行の1戦あたり 平均/中央値/最大 秒」。`--cand 0` では選出の一致数と再現（res+log）一致数を表示。

### 4.3 `item-report [--out path]`（既定 `logs/ITEM.md`）
保存済みのものから作る（途中でも出せる。未実行の候補は「未実行」）。slot4_8.json・cores_R9.json は読み取りのみ。

## 5. 判定（数字で決める）

- 「勝ち」は `res == 1`（判定勝ちを含む）。`res` が None は数えない。対の集合 P = 候補と slot4_8 の両方に結果がある (kid, k)。
- **採用**: P での候補の勝ち数 ≥ 基準の勝ち数 + 3（100戦そろっていれば **51勝以上**）。
- **現状維持（ゴツゴツメット）**: 差が −2〜+2 勝（僅差）。差が −3 以下も現状維持（悪化）。
- 複数の候補が採用条件を満たすときは**勝ち数が多い方**。同数なら候補番号の小さい方。
- 判定は100戦がそろった候補だけで行い、未完了の候補は「判定保留」。
- 追加条件は付けない（ユーザーの条件は平均勝率が上がること）。エアームドの選出試合の勝率などは参考として出すだけで判定に使わない。
- レポートに必ず「100戦で±10pt の誤差の中での判定である」ことを書く。
