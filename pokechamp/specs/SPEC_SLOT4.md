## 1. 前提（コードとデータで確認した事実）

### 1.1 パーティの読み込み（種族が R9 と違っても読める）
- `refine.apply_party(party)` は `_BASE_SPECIES`（最初に呼んだときの種族の並び）と一致しないと assert で止まる。持ち物の重複・努力値（合計66・各32以内）・技4つ（重複なし、`battle.MOVE` に存在）も assert する。
- `core_test._init_party(tag)` は `refine.load_tag(tag)` → `_BASE_SPECIES` を**そのパーティの種族に置き換えてから** `apply_party` → `battle.MY_TYPES` を `battle.TEAM` から作り直す → `refine.teams()`。docstring は「R9 と同じ種族」と書いているが、コードは種族の違いを許す（置き換えているため）。
- `refine.load_tag('S4_3')` は `R<数字>` 以外のタグを `data/party/S4_3.json` として読む。**よって候補の初期化は `core_test._init_party(f'S4_{n}')` でそのまま行える**（実測: 9 候補すべてで `apply_party` が通り、`battle.engine_game` で特性・持ち物・技4つが engine の ID に変換されることを確認。下表）。
- `apply_party` で更新されるもの: `battle.TEAM`・`battle.MY`（`my_sets()`）・`battle._OPP_CACHE`。`_init_party` が追加で `battle.MY_TYPES` を更新する。
- 更新されないもの: `infer._MY`（import 時に `team.py` から作る）。これは `infer.my_mon()`（観測＝被ダメ/与ダメ記録からの推定）でしか使われず、ブラインド対戦（`refine.blind_play`）は観測なし（`obs=()`）で `opp_sets` を呼ぶので**影響しない**。`team.py` は変えない。
- Windows（spawn）でも同じになるよう、ワーカー関数の先頭で毎回 `_init_party(tag)` を呼ぶ（冪等。R10 の `_work_adj` と同じ作り）。

### 1.4 既知の偏り（変えずに記録する）
- `battle.select` は `history_bonus`（実戦の記録 `KNOW['vs']`）を選出の点数に足す。記録があるのはガブリアス 17・アシレーヌ 15 試合ぶん（旧パーティ時代）で、R9 の6体と他の候補は 0。**候補 1・2・6 は選出にわずかな補正がかかる**。実運用と同じ挙動なので外さず、レポートに注記する。

## 3. 評価設計

### 3.1 条件（R9 の `off` と同じ）
- 選出規則・行動規則なし（`blind_play` の `rules=None`）。自分5手読み・相手3手読み、最大30ターン（`blind_play` の既定）、ブラインド（`know=False`）、`trace=True`（自分の技ごとの記録 `mv`。試合結果に影響しないことは adjust-selftest で確認済み）。
- 相手: `core_test.EVAL_IDS` の 20 構築。**相手の選出（`opp_order`）は `cores_R9.json` の `plan[kid]['opp_order']` をそのまま使う**（候補ごとに再計算しない。相手の3体と先発を R9 と揃えて対にするため）。
- 自分の選出: 候補ごとに `_init_party(f'S4_{n}')` のあと `refine.blind_select(t)`（`order_filter=None`）で再計算する。`[best, top3]` を保存。
- 種: `core_test.seed_of(kid, k)`（R9 の off と同じ）。k は段階1が 0,1,2、段階2が 3,4。

### 3.2 二段階
- **段階1**: 全9候補を k=0,1,2（20構築×3戦＝60戦）。基準は R9 off の同じ60戦＝**25勝**。
- **段階1の通過**: 勝ち数が **26 以上**（25 より多い）の候補のうち上位3つ。順位は (1) 勝ち数、(2) 新メンバーが選出された試合の勝率、(3) 新メンバーが選出された試合の勝ち数、(4) 候補番号の小さい方。通過が0なら段階2は行わず「採用なし（現状維持）」。
- **段階2**: 通過した候補だけ k=3,4 を追加（40戦）し、計100戦にする。
- 所要時間の見込み（R9 off の平均80秒/戦・4並列）: 段階1 540戦 ≈ 3時間、段階2 120戦 ≈ 40分、対照 7戦 ≈ 3分。選出の再計算は 1構築 約3秒（9候補で約10分）。**1候補ずつ（`--cand N`）実行し、終わるごとにチェックポイントを確認する**運用にする（コンテナが再起動しても、再実行すれば続きから回る）。

### 3.3 R9 の対照（`logs/refine/slot4_R9.json`）
- **再現確認**: R9（タグ `R9`）で、`EVAL_IDS` の先頭5構築の k=0（5戦）を、cores_R9 の `off` の選出・相手の選出・種で、本仕様のワーカー経由で再実行する。`res` と `log` が保存済みと一致した数を記録する（目標 5/5、4 未満なら本番を始めずに Opus に報告）。
- **欠けの補完**: `6abd49d970032380` の k=3,4（R9 off で未実行の2戦）を同じ方法で実行して保存する（cores_R9.json には書かない）。これで段階2の比較を 100 戦の対で行える。
- 選出の一致確認: R9 で `blind_select` を 20 構築ぶん再計算し、cores_R9 の `off.my_order` と一致する数を記録（目標 20/20）。

### 4.2 `slot4-run --cand N --games 3|5 [--procs P] [--max-games M]`
- `--cand 0` は R9 の対照（§3.3: 再現5戦＋欠け2戦＋選出の一致確認）。`--cand 1〜9` は候補。
- `--games 3` は k=0〜2、`--games 5` は k=0〜4（段階2）。済んだ試合は飛ばす。
- 結果ファイル `logs/refine/slot4_<N>.json`（N=0 は `slot4_R9.json`）:
  ```json
  {"version": 1, "cand": N, "tag": "S4_N", "sig": refine.sig(パーティ), "base_sig": refine.sig(R9),
   "source_sig": cores_R9.json の sig, "policy_version": policy.POLICY_VERSION, "depth": [5, 3],
   "plan": {kid: {"my_order": [...], "my_top": [[...], ...], "opp_order": [...], "sec": 秒}},
   "games": {"<kid>|<k>": blind_play の戻り値 + seed, sec, tag}}
  ```
  開くときに `version`・`sig`・`base_sig`・`source_sig`・`policy_version`・`depth` を照合し、違えば止める（`--force` で日時付きに退避して新規）。
- 選出（`plan`）は未計算の構築だけ計算し、**1構築ごとに保存**。試合は `multiprocessing` の Pool（fork、無ければ spawn）、`imap_unordered`、**1戦ごとに `safeio.write_json` で保存**（R9 の `cmd_run`・`_run_adj` と同じ作り）。
- ワーカー `_work_slot4(job)`: 先頭で `_init_party(tag)`、`refine.blind_play((party, kid, my_order, opp_order, seed, 5, OPP_DEPTH, False, None, True))`、例外は `{'res': None, 'error': ...}`。`seed`・`sec`・`tag` を付けて返す。
- 進捗表示: `[済/全体] kid8|k 勝/負 nT 秒 経過分`。例外は最後の1行を表示。最後に「この実行の1戦あたり 平均/中央値 秒」を表示する。
- `res` が None の試合は「未完了」扱いで、次の実行で再試行する。

### 4.3 `slot4-report [--out path]`（既定 `logs/SLOT4.md`）
保存済みのものから作る（途中でも出せる）。cores_R9.json・slot4_R9.json は読み取りだけ。
1. **条件**: §3.1 の条件、対照の数字（R9 off k0-2 25/60、k0-4 37/98＋補完2戦の結果）、作成日時、対戦の合計時間、1戦の所要時間（候補ごとの平均・中央値）。誤差の注記: 「60戦で±12pt、100戦で±10pt（95%）、並びごとは±20%程度。同じ相手・同じ種の対比較なので差の誤差はこれより小さいが、5勝未満の差は偶然で説明できる」。
2. **候補一覧**: 番号・種族＠持ち物・特性・性格・努力値・技・実数値・狙い（§2.1 の1行要約）・重なりの注記（§2.2）・`history_bonus` の記録の有無（§1.4）。
3. **段階1の表**（候補9行＋R9 行）: 勝ち/60、勝率、R9 との差（勝ち数）、新メンバーの選出試合数と勝率、通過（○/×）と順位。
4. **段階2の表**（通過候補＋R9 行）: 勝ち/100（R9 は 98＋補完2）、勝率、差、新メンバーの選出試合数と勝率、採用判定（§5.3 の各条件の ○×）。
5. **並び（C1〜C11）ごとの勝率**: 候補ごとに R9 off と並べる（`cores_of(kid)` を使う。重複ありで数える）。特に C2・C11・C1・C10・C8 を太字。
6. **構築ごとの選出の変化**: 構築 / R9 off の選出 / 候補の選出 / 各戦の ○× / 選出が R9 と同じ構築での結果一致率。
7. **新メンバーの使用技**: 候補ごとに技別の使用回数（`mv` の自分＝新メンバー）、命中/外れ/守られ/無効、倒した数（`faints` で同じターンに相手が倒れたもの）、場に出たターン数。
8. **採用判定**（§5.3）と、採用なら「R11 案 = S4_n の内容」を書く（`data/party/R11.json` は作らない。作るのはユーザーの確認後）。

## 5. 判定

### 5.1 数え方
- 「勝ち」は `res == 1`（判定決着を含む）。`res` が None の試合は数えない（未完了）。
- 「新メンバーが選出された試合」: その構築の `plan[kid]['my_order']` に候補の種族が入っている試合。R9 ではエンペルト。

### 5.2 段階1 → 段階2
§3.2 のとおり。勝ち数 26 以上の候補の上位3つ。

### 5.3 採用基準（段階2の100戦で判定）
対の集合 P = 候補と R9（cores_R9 の off 98戦＋slot4_R9 の補完2戦）の両方に結果がある (kid, k)。補完が終わっていなければ 98 戦で判定する。
- **条件A（全体）**: P での候補の勝ち数 ≥ R9 の勝ち数 + 3（R9 は 100戦なら 37＋補完ぶん）。差が 0〜2 勝は「僅差」として不採用（SPEC_ADJUST の純増+3 と同じ基準）。
- **条件B（新メンバー）**: 新メンバーが選出された試合が 10 戦以上あり、その勝率が R9 off のエンペルト選出試合の勝率（**12/25 = 48.0%**）以上。選出が 10 戦未満なら「判断不能（選出が少ない）」で不採用。
- A と B の両方を満たす候補を採用。複数あれば全体勝率が高い方、同率なら新メンバーが選出された試合が多い方、それも同じなら候補番号の小さい方。
- どれも満たさなければ「採用なし（R9 のまま）」。
- レポートには必ず「100戦での±10pt の誤差の中の判定である」ことを書く。
