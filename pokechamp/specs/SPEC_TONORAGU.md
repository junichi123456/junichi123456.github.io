## 3. 実行仕様（`python roundrobin.py tonorag {import,plan,run,report,selftest}`）
- `import`: §1 の A 取り込み（既にあれば何もしない。`--force` で再取得）。
- `plan`: T = rr_plan の teams ＋ `rr_team(A)` ＋ `rr_team(B)` ＋ `rr_team(C)`。`tn_plan.json`（`logs/refine/`）に version `tn1`、sig（sha256(rr_plan sig + L + 変種id + 各変種の team JSON + 相手選出 + 候補24 + resource設定 + 'tn1')）、相手選出リスト、候補24、深さ、deny [True,True]、resource 設定、変種の approx 一覧を保存。sig が違えば SystemExit（`--force` で旧を日時付き退避）。
- `run --stage 1|2 [--max-games N] [--retry-errors] [--procs 4] [--resource strict|loose|discount|off]`（既定 loose、§4）: ジョブ = counter の `ct_job/_job_ct` と同形で、L 側の選出＝候補、相手側＝固定選出。blind_play の引数は counter と同じ（excl=(s0,)、deny (True,True)、プレイブックは既定＝`_pb_args`。A〜C はガイドが無いのでトノラグ側はプレイブック無し、L 側は既存の規則）に、末尾 resx=(rc0, rc1) を足す（`_job_adapt` の a[9] と同じ合成: `pa=(pa[0] if pa else None, res)`）。
- 種 = `crc32(f"tn{V}{'/'.join(opp選出)}{'/'.join(L選出)}{k}")`（V＝変種記号 A/B/C。依頼の形に変種を加えたのは、ブリジュラス先発などの同名選出が変種間で同じ種にならないため）。
- 結果 `logs/refine/tn_games.json`（ヘッダ version, plan_sig, resource, playbook 署名）に **1戦ごと `safeio.write_json` で atomic 保存**、key＝`tn:{V}|{opp選出}|{L選出}|{k}`。再実行は未完・error のみ実行（`--retry-errors`）。行動ログは `tn_logs.jsonl`（`append_log` 形式）に1戦1行。レコードは ct_record の項目＋ `variant`, `opp_sel`, `depth`, `res_stats`（両側の res_on 回数・切った取り巻き）。
- 既存の `ct_*`, `m7_*`, `RES_AXIS`, M8_6 経路、既存 JSON/MD は変更しない。

## 4. 「被ダメ・瀕死はリソース」（両側）
既存の resource は refine.blind_play が既に **side ごと**に `resx[k]`（axis, opp6, loose）を受け付け、search の `_lookahead_res` は side i で動く。足りないのは roundrobin 側の軸の指定だけなので、`RES_AXIS` には触らず **`TN_AXIS = {L: ('リザードン','ムクホーク'), A/B/C: ('ラグラージ',)}`**（Mon.name＝元種族名）を新設し、両側に `{'axis':…, 'loose':…, 'opp6': 相手6体の元種族名}` を渡す。selftest で軸名が実際の State の mons 名に含まれることを assert。
- strict: 軸が相手の残り候補全員に勝てるときだけ取り巻きを割引。L は軸2体（メガは1体のみ）なので発動しうるが、トノラグ側は軸1体のため発動は稀の見込み。
- **loose（既定）**: 候補の80%に軸が勝ち、残りを取り巻きが受け持てるとき。雨下のメガラグラージ（すいすいで素早さ2倍、ウェーブタックル1.5倍）は `_res_beats` が State の天候を見るため、雨が残っている間は発動しやすい ＝『ニョロトノ／イエッサン／バサギリを切ってラグラージで勝つ』に近い動きを再現できる見込み。
- discount（代替）: 軸が生存していれば axis_cover を見ずに常に取り巻きを RES_W(0.4) で割引（search に関数を足さず、roundrobin で `cand` に空でない固定の判定を返す小さな包装関数を tonorag 専用に置く）。影響: ほろびのうた・だっしゅつボタン・いやしのねがいで取り巻きを切る動きは出やすいが、軸が勝てない局面でも取り巻きを安売りして負けが増えうる（L 側では「リザXが残るからミミッキュを捨てる」の過剰）。report に発動率と勝率を並べ、loose との差が±4pt 以内なら誤差扱い。
- 発動率（res_on の決定数/全決定数）を側ごとに report に出し、loose で10%未満なら discount での再検証を推奨（実行はユーザー判断）。off（従来）も同じ種で回せるようにして比較可能にする。

## 5. engine の扱い（確認済み・新規実装なし）
engine.py は Showdown gen9 champions の移植で、以下は実装済み: あめふらし→雨（1208行）、すいすい（雨で素早さ2倍、526行）、雨のみず1.5倍／ほのお0.5倍（1743行。リザXのフレアドライブ・アシレーヌのなみのりに影響）、サイコメイカー→サイコフィールド（1211行）、フィールドで接地対象への優先度>0の技を無効（2418行: ふいうち・かげうち・アクアジェット・しんそくが封じられる。いたずらごころ等も同じ経路）、ワイドフォース強化（1586行）、ほろびのうた（3461行、カウント4→3ターン後瀕死・交代で解除）、アンコール（979行）、まもる系（PROTECTS）、だっしゅつボタン（2688行）、レッドカード、いやしのねがい（1175行）、ばけのかわ、きあいのタスキ、ふうせん・サイコシード。技（ウェーブタックル・クイックターン・サイコノイズ・マジカルフレイム等）は dex.MOVES に全てある。selftest で各1局面の単体確認を行う（§7-5）。未実装は無し。ただし「ほろびのうたの3ターン先の瀕死」を読むには深さが要る（4手では終盤の詰め筋を見落としうる → 第2段を5手にする理由）。

## 6. レポート `logs/TONORAGU.md`（`tonorag report`）
1. 条件（変種・出典・**近似項目の一覧＝仮説**、深さ、種、resource 設定、所要時間）。
2. 変種×相手選出ごと: L の最良選出（勝率・Wilson 95%区間・戦数）、悪い選出トップ3。後発順2通りの勝率差（差が無ければ1行にまとめる）。
3. 変種ごとの最良選出（その変種の全相手選出平均、第2段があればそれを優先）と、**3変種共通の選出**＝変種別勝率の最小値（最悪ケース）が最大のもの（同率は平均で）。
4. 個体ごとの動き（tn_logs.jsonl から集計）: 個体ごとの先発率・行動の上位（何ターン目に何をしたか）、ほろびのうた被弾後の交代ターン、アンコールされた技と解除までのターン、ラグラージのメガ・雨の残りターンとラグラージを倒したターン/個体、イダイトウ・ミミッキュ・アシレーヌの先制技がサイコフィールドで封じられた回数。
5. こちらが倒されるパターン（負け試合の瀕死順の上位、ラグラージの雨下ウェーブタックル／じしんで何体抜かれたか）。
6. 型の変更案（技・努力値・持ち物のみ、**仮説**として列挙。負けパターンから機械的に: 例 アシレーヌのタスキ→別持ち物、ガブリアスの技（ステロ→げきりん等）、ミミッキュの型（トリル→かげうち以外）、ムクホーク／リザXの技）。検証は別仕様。
7. 結論: 「この相手（変種）にはこの選出・この立ち回り」を変種ごと＋共通で各1行。
